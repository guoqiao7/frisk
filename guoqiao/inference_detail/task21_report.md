# Task 21 工作汇报：让归约接入统一布局推断与贡献正确性验证

整理日期：2026-09-19。范围：M4 第三阶段中的 Task 21。

当前状态：Reduce 核心实现及受限范围内的回归测试已完成；完整 `MMA→Reduce→tile_store` 成功验收仍未完成，原因见第 8 节。不代表整个 Task 21 原契约或 M4 已全部验收。

## 1. 一句话概括

Task 21 让 Frisk 不仅知道“归约结果由哪些线程持有”，还能检查“每个输入有没有恰好计算一次、最终结果是否完整，以及线程之间需要怎样交换数据”。

例如，对矩阵逐行求和，编译器现在可以推导输出布局、选择确定性的归约方案、将方案写入程序，再根据实际程序独立复验。

与前两个任务的关系是：

- Task 19：解决 Copy、Fill、Parallel 的访问分工和写入责任。
- Task 20：解决矩阵乘加的输入、累加器和指令布局必须联合匹配的问题。
- Task 21：解决多个输入元素如何合并为一个结果，以及副本不能被重复计入的问题。

本次交付属于编译器的布局推断与静态验证，尚未生成可执行 GPU 归约内核，也没有性能提升结论。

## 2. 新增 Tensor 归约操作，明确计算语义

新增 `frisk.reduce_tensor`，支持沿一个维度求和、求最大值或求最小值，分别使用 `sum/max/min`。

### 2.1 具体例子：对 `64×64` 矩阵逐行求和

```mlir
// 未编码输入的操作示例；布局由推断补齐。
%result = frisk.reduce_tensor %src {kind = "sum", dim = 1}
  : tensor<64x64xf32> -> tensor<64xf32>
```

`dim = 1` 表示归约第 1 维，即列方向。结果保留 64 行，每行产生一个数：

```text
result[i] = src[i,0] + src[i,1] + … + src[i,63]
```

新操作产生一个新的 Tensor 值，不隐式覆盖输入、清零某块内存或写回输出。如果需要保存到内存，应再使用显式 `tile_store`。

当前支持输入和结果采用相同的 f16、bf16 或 f32 类型，不自动提升为 f32。输入至少二维，所有维度必须是大于 1 的静态二次幂；一维归约成标量、动态形状和非二次幂形状暂不支持。

### 2.2 对浮点语义作出明确约定

- `sum` 允许并行重结合：选定布局后使用确定的归约树，但不保证与串行从左到右相加逐 bit 相同。
- `max/min` 传播 NaN，并按约定区分正零与负零；不是忽略 NaN 的另一类最大值/最小值操作。
- 不继承旧 Reduce 中的目的内存、`clear` 等隐式行为；旧操作的自动转换留给后续任务。

因此，本次不是把旧 Reduce 换个名字，而是为新 Tensor 路径建立清晰的数学和布局契约。

## 3. 自动推导归约后的布局

布局描述的是“哪个线程的哪个寄存器持有哪个元素”。矩阵删掉一个归约维度后，输出布局不能简单照搬输入布局。

Task 21 会先从输入坐标中删除归约维度，再压缩不再需要的寄存器区分位，重新计算寄存器槽数与重复持有关系。

### 3.1 一个直观例子

假设某线程的 4 个寄存器分别持有同一行的 4 列：

```text
输入：r0 → (第 i 行，第 0 列)
      r1 → (第 i 行，第 1 列)
      r2 → (第 i 行，第 2 列)
      r3 → (第 i 行，第 3 列)

按列归约后：这 4 个位置都对应输出的“第 i 行”
```

原本用来区分这 4 列的寄存器坐标位，已经不能区分不同输出。输出不必机械保留这 4 个独立槽位。

实际实现还处理 XOR 映射和非零但线性相关的寄存器位，不是只删除映射中变成零的部分。它保留原有线程组织，得到与输入相对应的“自然输出布局”。

这里的投影只回答结果应如何分布，并没有执行加法。真正检查这些输入如何合并，是下一节的贡献证明。

## 4. 核心能力：区分“不同加数”和“同一个加数的副本”

一个逻辑元素可能被多个线程同时持有。对普通读取，这些副本可以都存在；对求和，如果把每个副本都算进去，结果就错了。

### 4.1 具体例子：正确结果是 10，不能是 20

某一行有 4 个不同元素：

```text
逻辑输入：[1, 2, 3, 4]
```

假设每个元素都被两个物理位置持有，那么物理上有 8 份数据，但逻辑上仍然只有 4 个加数。

Task 21 的处理是：

1. 根据逻辑坐标识别同一元素的多个副本。
2. 每个元素只选一个确定的代表持有者参与计算。
3. 按规范顺序构造归约树。
4. 将完整结果分发给输出布局要求的全部持有者。

假设所选代表的物理顺序恰好对应 `[1,2,3,4]`，树可以表示为：

```text
1 + 2 → 3 ┐
          ├→ 10 → 输出持有者 A：10
3 + 4 → 7 ┘     → 输出持有者 B：10
```

要拒绝两种不同的错误：

- 把输入副本也当作额外加数，得到 20。
- 把尚未合并的 3 和 7 当作两个“同值输出副本”。

输出副本必须各自持有完整结果 10，而不是各自持有一部分和。

### 4.2 归约树可确定、可重新核验

代表持有者按照线程块、warp-group、warp、lane、寄存器的位置顺序确定，再相邻配对、逐层合并。这个顺序由实际布局决定，不一定等于逻辑下标顺序。

验证会检查：每个输出所需的输入是否完整、是否重复贡献、是否混入其他行的数据，以及完整结果是否分发到所有应有位置。测试也包含物理顺序不同于逻辑顺序的情况。

这比单纯检查“布局覆盖了所有元素”更进一步：覆盖正确，并不能自动证明归约计算正确。

## 5. 明确归约需要多大范围的通信

归约输入可能在同一线程，也可能分布到多个线程。Task 21 根据归约树和结果分发的实际依赖，记录通信范围：

| 范围 | 通俗含义 | 例子 |
| --- | --- | --- |
| `register` | 同一线程内部即可完成 | 一行的所有输入都在该线程寄存器中 |
| `warp` | 同一个 warp 内的不同 lane 需要交换数据 | 同一行的输入分散在一个 warp 中 |
| `cta_shared_tree` | 同一个线程块内需要跨 warp 或 warp-group 合并/分发 | 一行的输入分布在多个 warp 中 |

范围既考虑输入合并，也考虑完整结果的分发，不能只看输入加法发生在哪里。

当前记录的是“必须实现哪些通信依赖”，并未生成 shuffle 指令、分配共享内存或插入 barrier。尤其是跨 warp 方案，后续生成 GPU 指令时仍须落实资源分配和同步，不能仅凭这份静态证明就声称 GPU 执行安全。

## 6. 接入统一约束求解，保留显式转换边界

Task 21 新增专门的二端点关系 `ReductionLayout`，连接“Reduce 实际消费输入的位置”和“Reduce 结果”。

```text
生产者 Tensor
      │ Convertible：需要时在使用点转换
      ▼
Reduce 输入消费位置
      │ ReductionLayout：投影与贡献关系
      ▼
自然输出 Tensor
      │ Convertible：后续使用者可另需转换
      ▼
后续操作的消费位置
```

这里不能用 `SameLayout`，因为输入与输出形状不同；也不能当作普通转置，因为归约删掉的信息无法通过逆变换恢复。

### 6.1 正向产生输出候选，反向筛选已有输入候选

对每个合法输入候选，先计算对应的自然输出布局，再建立有限的合法“输入—输出”组合。下游提出输出要求时，删除不再有合法组合支持的输入候选，而不是反向凭空恢复归约维度。

例如，假设输入候选 S1 只能得到输出 D1，S2 只能得到 D2；若最终要求 D2，则可以排除 S1。此例仅解释筛选机制，不代表实际候选数量。

当前每个变量最多 4 个候选，一条归约关系最多检查 16 对组合；候选集合冻结后只删不增。归约结果也不会被下游反向建议随意改成非自然布局：下游需要其他布局时，由使用点的转换关系处理。

### 6.2 具体例子：继承 MMA 的 128 线程环境

Task 20 的 MMA 可以产生由 128 线程持有的 `128×128` Tensor。后续按行 Reduce 会继承可确定的 128 线程环境，而不是无条件套用普通操作的 32 线程缺省值。

显式转换建立了新的线程环境时，后续推断也会尊重该边界，不再错误地一直追溯到更早的生产者。对于真正要求同布局的关系，独立来源的线程冲突仍然会报错。

本次复审修复并测试了两类问题：下游候选污染自然结果，以及线程推断越过已确定的转换边界。

## 7. 方案写进程序，并根据实际结果独立复验

求解成功后，操作上写入 `frisk.reduction_contract` 与 `frisk.execution_threads`。

归约契约包含 12 个严格检查的字段，记录版本、目标、归约种类与轴、类型、输入/输出形状、线程数、算法、输入代表选择策略、输出分发策略和通信范围。

最后的检查不依赖“求解器之前说过这是对的”，而是从实际 Tensor 编码和操作属性重新构造规范依赖并核验；不会重新生成候选、重新搜索方案或偷偷补上缺失转换。

例如，把实际方案需要的跨 warp 通信篡改成 `register`，或者删除契约字段、改错线程数，都会被拒绝。

物化仍采用事务方式：先在临时程序中改写，验证成功才更新原程序；失败保留原程序不变。测试还检查打印后重新解析，以及二次推断结果保持稳定。

## 8. 集成结果与尚未完成的验收项

已验证的场景包括逐行归约、三维张量删中间轴、连续两次归约、转置后归约、外部显式编码转换，以及循环和 Parallel 线程环境。

两段重要集成均已验证成功：

- `128×128 MMA 结果 → 按行 Reduce`：可继承 MMA 的 128 线程环境。
- `Reduce → Global tile_store`：后续写入使用完整归约结果，并检查写入责任。

但是，完整 `MMA→Reduce→tile_store` 目前不能通过成功验收。原因不是归约数学不成立，而是同一个连通约束图包含 9 个变量：

| 部分 | 新增变量 | 数量 |
| --- | --- | --- |
| SS MMA | A/B 存储、init 生产者、init 消费位置、MMA 结果 | 5 |
| Reduce | 输入消费位置、归约结果 | 2 |
| tile_store | 写入消费位置、目标存储 | 2 |
| 合计 | 同一连通分量中的布局变量 | 9 |

现有初版求解器限制每个连通分量最多 8 个变量，用于控制组合搜索规模。这是编译器的工程预算，不是 GPU 的硬件上限。

本次没有擅自提高上限，也没有合并应独立表示的生产者与消费位置。完整链测试验证的是“确实有 9 个变量并明确拒绝超限”，不是整链推断成功。

因此，当前准确结论是：受限实现与回归完成，原契约的完整链成功验收仍未完成。后续需要单独确认调整求解预算，或设计保持语义的等价变量压缩方案。

上一轮实现验证的结果如下；本报告引用该实测记录，本次整理文档没有重新运行测试。

| 测试类别 | 结果 | 主要验证内容 |
| --- | --- | --- |
| 全量单元测试 | 197/197 通过 | 数学规则、布局证明、候选求解与集成 |
| 全量 lit 测试 | 36/36 通过 | 真实文本 IR 的推断、诊断与稳定回放 |

Task 21 新增 32 项单元测试，其中数学/属性规则 4 项、投影/贡献证明 13 项、图集成 15 项；新增 2 份 lit 测试文件。

重点反例包括重复求和、遗漏输入、部分和冒充完整副本、跨行混合、漏分发、错误布局投影、线程冲突、属性篡改和证明预算超限。逻辑点与硬件点的枚举分别受 65536 点预算约束，预算不足不能当作证明成功。

旧 Reduce 测试也进行了分类：可用的持有关系以独立坐标计算核对；错误 replication、丢失 batch 坐标等旧样例作为反例，不为保持旧结果而保留错误。旧 16 线程样例与当前至少 32 线程的支持集明确区分。

当前未完成的范围还包括：动态/非二次幂形状、标量输出、未合并部分和的专用表示、旧 Buffer Reduce 自动转换，以及 GPU 指令生成、数值执行和性能评测。

## 10. 汇报时可以这样概括

> Task 21 将归约接入了 Frisk 的统一布局系统。它能够推导归约结果的线程和寄存器分布，保证每个逻辑输入只贡献一次，区分完整结果副本与尚未合并的部分和，并记录必要的线程间通信。方案写入程序后，还会依据实际布局独立复验。当前受限实现通过了全部 197 项单元测试、36 项 lit 和 4 项 CTest；MMA→Reduce、Reduce→store 分段集成已通过，但完整链因 9 个变量超过现有 8 变量预算仍未完成成功验收。GPU 指令生成与性能优化属于后续工作。
