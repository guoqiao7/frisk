# Frisk 已实现功能介绍

> 范围：当前已完成的 M0–M3 布局系统。

## 一句话介绍

Frisk 已经能为一部分 GPU 张量程序自动安排数据布局：描述“数据放在哪里、由哪个线程持有”，协调不同算子的布局要求，并在需要时插入数据交换。

## 1. 能描述数据在内存和线程中的位置

系统区分两件事：**内存布局**描述元素的地址，**线程布局**描述谁持有元素。

例如，有四个 FP16 元素 `[10,20,30,40]`：

- 在连续内存中，它们从第 0、2、4、6 字节开始存放。
- 在线程中，可以让 lane 0～3 分别持有一个元素；也可以让每个线程都持有完整四个元素。

逻辑数据完全相同，存放方式可以不同。

作用：不再把“矩阵长什么样”和“数据怎么放”混在一起，为自动选择布局提供统一表达。

## 2. 能计算布局之间的关系

已经实现映射组合、坐标置换，以及位矩阵的转置、求逆和右逆等基础运算。

例如，已知“lane 2 持有第 3 个元素”，又知道“第 3 个元素位于第 4 字节”，系统就能组合得到：**lane 2 应读取第 4 字节**。

反过来，如果要找某个元素由谁持有，也可以通过逆映射寻找；存在多个副本时，右逆可以选出一个合法持有者。

作用：为地址计算、布局转换和正确性检查提供数学基础，而不必为每种布局手写一套规则。

## 3. 能绑定并传播内存布局

这里的“绑定”是给一块已有内存说明元素怎样存放；“传播”是根据操作之间的关系，自动补齐其他内存的布局说明。

### 具体例子：把四个元素从全局内存复制到共享内存

假设有两块已经分配好的缓冲区：

- 源缓冲区 G：位于 Global Memory，存着四个 FP16 元素 `[10,20,30,40]`，按连续方式存放。
- 目标缓冲区 S：位于 Shared Memory，可以容纳四个 FP16 元素，但尚未绑定 Frisk 存储布局。

程序要做的是将 G 的四个元素整块复制到 S。

### 第一步：给源内存绑定布局

每个 FP16 元素占 2 字节，因此源布局的规则很简单：**下标 i 对应的字节偏移是 `2 × i`**。

通过 `layout_view`，可以把这条规则附加到 G 上。得到的源视图仍指向 G，不是新申请的一块内存，也不会把 `[10,20,30,40]` 复制一份。

可以把它理解为给缓冲区贴上标签：“这里的第 i 个元素，从第 `2 × i` 字节开始读取。”

### 第二步：沿着整块 copy 关系传播布局

源视图有明确布局，目标视图没有绑定布局，两者由整块 `frisk.copy` 连接。当前推断会把源的元素偏移规则传播给目标，并保留各自的内存空间：

```text
推断前：源视图 = Global + 偏移规则 2×i
        目标视图 = Shared + 尚未绑定布局

推断后：源视图 = Global + 偏移规则 2×i
        目标视图 = Shared + 偏移规则 2×i
```

这不是把目标改成 Global Memory，而是让它在 Shared Memory 中采用相同的元素排列方式。

### 第三步：用具体地址理解复制含义

用 `G_base` 和 `S_base` 分别表示两块缓冲区的起始地址，则复制所表达的对应关系是：

| 元素下标 | 示例数值 | 源地址          | 目标地址        |
| -------- | -------- | --------------- | --------------- |
| 0        | 10       | G_base + 0 字节 | S_base + 0 字节 |
| 1        | 20       | G_base + 2 字节 | S_base + 2 字节 |
| 2        | 30       | G_base + 4 字节 | S_base + 4 字节 |
| 3        | 40       | G_base + 6 字节 | S_base + 6 字节 |

例如，数值 30 应从 `G_base + 4` 读取，写到 `S_base + 4`。元素的位置关系已经明确，目标一共需要 8 字节容量。

要区分：**`layout_view` 负责说明怎么放，布局推断负责补齐说明，`copy` 才表达搬运数据的操作。** 推断过程本身只修改程序中的布局信息，不会执行这次内存复制；这里也不代表已经完成可运行的 GPU 拷贝内核。

这个例子对应已有测试中的 `materialize_copy`：源显式绑定连续 Global 布局，推断后目标视图获得连续 Shared 布局。

作用：用户不必在拷贝两端重复填写相同的排列规则，编译器可以沿着数据关系补齐。对于同一底层内存的多个 `layout_view`，系统还会检查绑定是否一致，避免同一块数据被解释成两种互相冲突的排列。

当前支持的是这种**静态、形状和元素类型相同、两端都有 `layout_view` 的整块拷贝**，不包括带索引的局部切片或动态拷贝，也不会自动扩大原有内存分配。

## 4. 能自动补齐张量程序的布局

第 3 节解决的是“元素在内存的哪个地址”，这一节解决的是“张量参与计算时，由哪个线程持有哪些元素”。对于当前支持的程序，用户可以先写计算逻辑，不必给每个张量手工指定线程布局。

### 具体例子：对四个元素做逐元素加法

假设输入是四个 FP32 元素 `x = [10,20,30,40]`，函数计算 `y = x + x` 并返回。逻辑结果应为 `[20,40,60,80]`。

推断前的程序可以只写：

```mlir
func.func @elementwise(%x: tensor<4xf32>) -> tensor<4xf32> {
  %y = arith.addf %x, %x : tensor<4xf32>
  return %y : tensor<4xf32>
}
```

这里的 `tensor<4xf32>` 只说明“有四个 FP32 元素”，没有说明由哪些线程持有。`arith.addf` 表达逐元素相加，不需要用户在这里手工展开线程编号和寄存器位置。

### 第一步：识别哪些位置的布局需要协调

系统会分析输入 x、加法结果 y，以及函数返回值之间的关系。

对于这个例子，两个加法操作数都是 x，让输入和输出采用相同布局，就可以在对应位置完成 `y[i] = x[i] + x[i]`；返回值也可以继续使用这个布局，不需要额外交换数据。

这不是简单地给所有张量统一贴一个标签，而是先看具体操作的要求。例如，逻辑转置需要按行列交换来关联输入、输出布局，不能直接照搬加法的关系。

### 第二步：选择具体的线程分配方案

系统生成候选布局，再选出满足这些关系的方案。现有加法测试实际选出的布局是：一个 warp 中有 32 个 lane（即 32 个线程），lane 编号除以 4 的余数决定它持有哪个元素。

| 线程编号              | 持有的输入 | 对应的加法 | 持有的输出 |
| --------------------- | ---------- | ---------- | ---------- |
| lane 0、4、8、…、28  | x[0] = 10  | 10 + 10    | y[0] = 20  |
| lane 1、5、9、…、29  | x[1] = 20  | 20 + 20    | y[1] = 40  |
| lane 2、6、10、…、30 | x[2] = 30  | 30 + 30    | y[2] = 60  |
| lane 3、7、11、…、31 | x[3] = 40  | 40 + 40    | y[3] = 80  |

因此，每个线程持有一个元素，每个逻辑元素在不同线程中有八份副本。这就是布局中的 `replication = 8`。

**八份副本不意味着张量变成了 32 个不同元素。** 逻辑上的 x 和 y 仍各有四个元素，只是物理持有方式存在重复。表中的数值用于解释选定布局的计算含义，并非本次已经运行 GPU 得到的结果。

### 第三步：把选择写回整个程序

选出布局后，系统不仅更新加法结果，还会同步更新函数输入、操作数和返回类型。用“布局 A”简写上面的线程分配方案，变化如下：

```text
推断前：输入 x = 四元素张量，未指定布局
        加法 y = x + x，未指定结果布局
        函数返回 = 四元素张量，未指定布局

推断后：输入 x = 四元素张量 + 布局 A
        加法 y = x + x，输入与结果均使用布局 A
        函数返回 = 四元素张量 + 布局 A
```

在实际程序中，这体现为张量类型附带 `#frisk.distributed<...>` 编码。加法的逻辑含义没有变化，变化的是编译器现在明确知道每个元素由谁持有。这个例子中各处布局相容，因此不需要插入 `convert_layout`。

### 不止加法：也能处理支持范围内的数据流和控制流

目前已覆盖整块读写、张量常量、支持的逐元素运算、逻辑转置、函数参数与返回，以及 if/for/while 中的布局传递。例如：

- 常量张量：不仅给常量结果补布局，也同步更新保存常量内容的类型。
- if 分支：两个分支的结果布局不同，可以在必要的分支出口插入转换，使合并后的结果符合统一要求。
- for 循环：协调初始值、循环内携带的张量和下一轮传回的值，避免循环前后布局不匹配。

作用：用户主要描述“要算什么”，编译器负责在支持范围内补齐“数据怎样分配给线程”，并保证相关位置一致。

当前仍是小规模静态程序的布局推断：已有显式布局会作为必须遵守的要求，未知算子不会被随意猜一个布局。上述八份副本是当前例子选出的合法方案，不代表性能最优；补齐布局也不等于已经生成并执行了完整 GPU 内核。

## 5. 能只转换需要换布局的那一条使用路径

同一个张量被多个算子使用时，不必为了一个算子而改变所有使用方。

例如，张量 x 使用布局 A：一个使用方直接接受 A，另一个使用方需要 B。

```text
x（布局 A）────────────→ 使用方 1
          └→ 转换 A→B → 使用方 2
```

系统保留原来的 x，只在第二条路径插入 `convert_layout`。

还可以清理多余转换：A→A 直接消除；没有其他使用需要时，A→B→A 的往返也可消除，A→B→C 可合并成 A→C。

作用：满足各个使用方的要求，同时减少不必要的数据交换。当前小规模求解器优先减少新增转换次数，并不代表已经找到了性能最快的布局。

## 6. 能根据数据来源选择三种交换方式

已经实现布局转换的规划与 GPU 测试降级：

| 数据在哪里               | 例子                          | 生成的处理方式                    |
| ------------------------ | ----------------------------- | --------------------------------- |
| 当前线程自己的寄存器里   | 需要的元素已经有本地副本      | 直接取本地寄存器                  |
| 同一个 warp 的其他线程里 | lane 1 需要 lane 2 持有的元素 | shuffle 交换                      |
| 另一个 warp 里           | warp 0 需要 warp 1 持有的元素 | 经 Shared Memory 写入、同步、读回 |

例如，跨 warp 重排 64 个 FP16 元素，需要 128 字节共享中转空间。存在副本时，系统会为每个元素选择唯一写入者，避免重复写冲突。

作用：把抽象的“换一种布局”落实为具体的数据运输步骤。这里目前是**生成并验证中间代码的测试能力**，尚不是完整可执行的 GPU 内核流水线。

## 7. 能检查错误，并避免留下改了一半的程序

系统会检查布局是否覆盖所需元素、地址是否重叠、分配容量是否足够，以及不同要求是否冲突。

例如，四个 FP16 元素紧凑存放只需 8 字节；如果指定它们从 0、4、8、12 字节开始存放，最后一个元素结束于第 14 字节，原来的 8 字节缓冲区就不够，系统会明确报错。

修改程序时也会先在暂存副本中完成重建与检查，全部通过才替换原程序。

作用：既能指出不合法的布局，也能避免推断失败后留下部分修改的程序。

## 8. 能复用一部分旧布局实现

旧 GEMM/Reduce 布局逻辑仍然存在，并已有适配器将部分旧布局转换为新表达，再逐点检查两者是否一致。

例如，旧布局说“元素 37 在线程 5 的寄存器 1 中”，转换后的新布局也必须表达同一个持有关系。

作用：让新系统能以已有实现作为迁移和校验基础。但这不等于旧 GEMM/Reduce 已经全部接入新的自动推断流程。

## 边界

当前是一个已经可工作的有限原型，主要面向 SM90/SM90a 和小规模静态程序；分布式张量推断目前要求各维大于 1 且为二次幂。

完整的硬件性能成本优化、旧 GEMM/Reduce 等算子全面接入新系统，以及完整 GPU 内核执行链还没有完成，不能宣称已经能够自动生成最优 WGMMA/TMA 内核。

可以概括为：**目前已经打通“表示布局 → 自动推断 → 插入必要转换 → 验证结果”的主流程，并能在测试范围内把转换展开为寄存器、shuffle 或共享内存交换。**
