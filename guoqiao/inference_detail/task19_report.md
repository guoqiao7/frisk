# Task 19 工作汇报：让 Copy、Fill、Parallel 接入统一布局推断

整理日期：2026-09-19。范围：M4 第二阶段的 Task 19，不代表整个 M4 已完成。

## 1. 一句话概括

Task 19 将 Copy（复制）、Fill（填充）和 Parallel（并行执行区域）接入新的布局约束体系，使编译器不仅知道“数据放在哪里”，还能够明确并检查“哪些线程负责哪些元素、谁能写入、能否按要求进行向量访问”。

Task 18 重点解决同一存储的不同视图、循环中的布局传递和有限候选收敛。Task 19 在这些基础上，把布局关系进一步落实到具体的复制、填充与并行操作。

本阶段主要完成：

- Copy 不再强制源和目的使用相同的物理地址公式，允许不同存储布局之间按逻辑元素复制。
- Fill 和 Copy 能明确实际写入者，拒绝重复写入、覆盖缺失等不合法方案。
- 根据线程的元素分工，检查向量访问的连续性、对齐和完整性。
- Parallel 的线程数成为真正参与候选生成、筛选和最终核验的约束。
- 将选定的执行要求写入实际 IR，并重新核验；失败时不留下改写一半的程序。

这里交付的是布局推断与正确性验证能力，不是已经生成完整 GPU 内核，也不是已经证明性能提升。

## 2. 将“数据怎么放”和“线程怎么分工”分开表达

可以把这两件事理解为仓库中的“货架位置”和“工人分工”：知道货物放在哪个货架，并不能自动知道由哪个工人负责搬运。

对应到程序中：

- **存储布局**：逻辑元素对应哪个内存地址，仍由 `layout_view` 上的布局描述表达。
- **执行布局**：线程和寄存器对应哪些逻辑元素，由 Copy/Fill 自身新增的执行属性表达。

Task 19 保留原有 MemRef 形式的 Copy/Fill，没有为了表达执行布局而虚构一个 Tensor SSA 值，也没有改变其 MemRef 类型。

推断成功后，原操作会保存四项信息：

| 属性                        | 通俗含义                         |
| --------------------------- | -------------------------------- |
| `frisk.execution_layout`  | 哪个线程、哪个寄存器对应哪个元素 |
| `frisk.execution_threads` | 使用多少线程                     |
| `frisk.writer_policy`     | 多个持有者中，哪些允许实际写入   |
| `frisk.vector_bytes`      | 要求满足多宽的访问契约           |

程序没有指定时，当前默认使用 `first_owner` 写入策略和宽度 1 的标量/packed 访问基线。没有外层 Parallel、也未显式指定线程数时，默认使用 32 线程；在 Parallel 中则使用其规定的线程数。

程序显式指定的属性是硬要求。推断不能为了成功而偷偷改掉线程数、换掉显式布局，或降低要求的向量宽度。

## 3. Copy：允许不同存储布局之间按逻辑元素复制

### 3.1 解决什么问题

旧的受限 Copy 推断要求源、目的存储布局的 map 相同。但复制的本意是“把源的某个逻辑元素交给目的的对应元素”，并不要求两边的物理存储顺序相同。

Task 19 改为分别检查读取和写入：同一个执行者对应逻辑坐标 `(i,j)`，读取源的 `S_src(i,j)`，写入目的的 `S_dst(i,j)`。

### 3.2 具体例子：行主序复制到列主序

假设 A、B 是两块独立且不重叠的 `2×2` 存储，每个元素为 4 字节的 f32。A 按行存储，B 按列存储：

```text
A 的逻辑内容：       Copy 后 B 的逻辑内容：
[10, 20]            [10, 20]
[30, 40]            [30, 40]

A 的地址公式：8i + 4j
B 的地址公式：4i + 8j
```

下面的偏移分别相对于 A、B 各自的内存起点：

| 逻辑坐标  | 元素值 | 从 A 的哪个字节读取 | 写到 B 的哪个字节 |
| --------- | ------ | ------------------- | ----------------- |
| `(0,0)` | 10     | 0                   | 0                 |
| `(0,1)` | 20     | 4                   | 8                 |
| `(1,0)` | 30     | 8                   | 4                 |
| `(1,1)` | 40     | 12                  | 12                |

复制完成后，A 的物理顺序是 `[10,20,30,40]`，B 的物理顺序是 `[10,30,20,40]`，但两者的逻辑矩阵相同。

Task 19 已有测试验证这类不同存储布局的 Copy 可以通过推断与核验。这里是改变存储排布的逐元素复制，**不是将逻辑矩阵转置**，也不表示已经生成相应 GPU 搬运指令。

### 3.3 能双向利用信息，也会检查重叠风险

已知源布局，可以向目的提供有限的候选建议；已知目的，也可以反过来给源提供建议。但不是原样复制绝对地址：跨不同底层存储时，要重新计算地址原点，并检查目的容量和对齐保证。

这些建议只在候选准备阶段生成。候选集合冻结后，传播阶段只排除不合适的方案，不无限来回生成。

此外，复制不意味着源、目的就是别名。新增的 `CopyAccess` 关系与 Task 18 的 `AliasLayout` 分工不同：

- `AliasLayout` 检查同一底层存储上的不同视图是否一致。
- `CopyAccess` 检查复制两端的逻辑域和已知重叠条件，不要求地址公式相同。

例如，已知 A 是同一块底层数组，复制 `A[0:4] → A[2:6]` 会涉及非恒等重叠，当前拒绝；`A[0:4] → A[4:8]` 完全不相交，或者复制到自身的相同逐点地址，则可在满足其他条件时接受。

对两个独立的 MemRef 参数，编译器不能仅凭参数名字不同就证明运行时不重叠；非重叠仍是调用者需要满足的 Copy 前置条件。

## 4. Fill 与 Copy：区分“持有元素”和“实际写入”

一个逻辑元素可能被多个线程持有，但不能据此让所有线程都写同一个位置。Task 19 为 Fill 和 Copy 的目的端加入了明确的写入者策略。

### 4.1 具体例子：32 个线程填充 4 个元素

假设要把数组 B 的 4 个元素全部填成 0，采用如下示意执行分布：

```text
线程 t 对应元素 B[t % 4]，t 的范围是 0～31。

B[0] 的持有者：线程 0、4、8、12、16、20、24、28
B[1] 的持有者：线程 1、5、9、13、17、21、25、29
B[2] 的持有者：线程 2、6、10、14、18、22、26、30
B[3] 的持有者：线程 3、7、11、15、19、23、27、31
```

每个元素都有 8 个持有者，但实际写入可以有两种规定：

- `all`：所有持有者都写。本例每个元素会被写 8 次，不满足唯一写入者契约，因此拒绝。即使填入的是相同常数，也不会因此绕过检查。
- `first_owner`：只允许每个元素的第一个规范持有者写。本例由线程 0、1、2、3 分别写 B 的四个元素，其他持有者不写，因此可以通过对应的所有权检查。

“第一个”不是依赖遍历顺序随机选取，而是按 `(cta, warp_group, warp, lane, register)` 的固定字典序确定。编译器还会检查所有元素都有持有者，不能只保证“不重复写”，却遗漏部分元素。

Copy 的目的写入遵守相同规则；重复读取可以合法，但不意味着允许目的端重复写入。

`first_owner` 已经写入实际 IR，并经过静态验证。未来生成 GPU 指令时仍需要真正执行这一选择规则；本阶段没有生成完整的写入谓词代码。

## 5. 向量访问：不仅看总共多少字节，还看同一线程是否连续持有

Task 19 支持的访问宽度为 `{1,2,4,8,16}` 字节。其中宽度 1 是标量/packed 基线，不表示把一个 f32 强制拆成单字节指令；更宽的访问需要额外证明。

例如要求 `vector_bytes=16`，对 f32 而言，一个完整向量块可以包含 4 个元素。考虑同一个线程的四个连续寄存器位置：

```text
情形一：对应物理字节偏移 0、4、8、12。
        若根指针有 16 字节对齐保证，且四个元素都由该线程实际访问，
        则这一块可以满足 16 字节向量访问要求。

情形二：对应物理字节偏移 0、8、16、24。
        地址不连续，不能按同一个 16 字节向量块访问。

情形三：偏移仍为 0、4、8、12，但分别由四个线程各持有一个。
        不能把四个线程的标量访问算成一个线程的向量访问。
```

检查还包括块起点对齐、没有越界、没有不完整尾部，以及选定写入者后是否出现向量块缺口。Copy 的源端和目的端都要满足要求，不能只证明读取连续就认为写入也连续。

不满足要求的候选会被删除；如果显式布局与显式宽度无法同时满足，就报告冲突，而不是静默降低宽度。

对齐依据可以来自 allocation 的显式保证，也可以来自 Task 18 允许的完整根 `layout_view` 前置契约。**操作要求访问 16 字节，并不能反过来证明根指针一定对齐到 16 字节。**

## 6. Parallel：让线程数真正影响推断，而不只是一个标注

当前支持的线程数为 `32、64、128、256、512、1024`，限定在单个 CTA，即一个 GPU 线程块内。

以 `threads=128` 为例，目标模型可以生成 `32 lanes × 4 warps × 1 warp_group` 的默认线程组织。寄存器数量不乘入线程数；这一组织也不等于已经选择 WGMMA 矩阵指令。

Task 19 将线程环境接入三个环节：

1. 准备候选时，生成符合该线程环境的布局，而不是始终只准备固定线程数的方案。
2. 筛选和求解时，排除不符合线程资源要求的候选。
3. 最终核验时，再检查实际 IR 的线程数与布局组织是否一致。

如果在 128 线程 Parallel 中显式要求 Copy/Fill 使用 32 线程，或者给它绑定仅符合 32 线程环境的执行布局，就会拒绝。

另一个重要场景是外部 Tensor 被内部使用。假设外部 Tensor 已有 32 线程布局 L32，而 Parallel 内部使用 128 线程布局 L128，推断会在必要的消费位置插入显式布局转换，再让内部计算使用 L128；不会因为一次内部使用，就把外部生产者的布局整体改掉。该行为已有专项测试覆盖。

## 7. 结果可检查，失败不污染程序

Task 19 不是只在推断过程中临时记住一个答案，而是形成完整闭环：

```text
收集操作要求 → 准备有限候选 → 排除不合法方案 → 选择布局
                                                    ↓
原程序保持不变 ← 核验失败 ← 在临时 IR 中写入布局并独立核验
                                                    ↓ 核验成功
                                              替换原程序
```

独立核验从实际 IR 中读取结果，不重新生成候选，也不猜测缺失属性。如果四项执行属性缺失，或被改成违反契约的值，就不能靠旧的候选缓存蒙混过关。

相关测试还确认：

- 推断失败后，原 IR 保持不变。
- 推断后的程序可以打印、重新解析；再次推断的输出与第一次逐字一致。
- 新 pass 不调用旧 Parallel 的递归布局推断方法。旧方法仍保留供兼容性测试使用，隔离结论来自真实调用计数。

为保证这些流程成立，本阶段还修复了 Kernel、Parallel、Copy 的相关打印和解析问题，并补充了对真实 Kernel 入口静态 MemRef 存储根的识别。

## 8. 验证结果与当前边界

根据 **2026-09-16 Task 19 实现验收记录**：

- 单元测试：129/129 通过，相比 Task 18 新增 25 项，其中操作集成测试 16 项、执行证明测试 9 项。
- lit 回归：32/32 通过，新增 2 份 Copy/Fill/Parallel 正反例及回放测试文件。
- CTest：4/4 通过，原有相关测试一并回归。
- 独立复审发现的视图与地址表不匹配、物理区间重叠及空参数 Kernel 回放问题均已修正，无剩余阻断项。

本报告整理时核对了实现记录、相关源码和测试用例，未重新构建或运行上述测试；这些数字是实现验收结果，不是新的性能测试结果。

当前仍有明确边界：

- Copy 只支持同 shape、同元素类型的静态整块复制，两端须为直接 `layout_view` 结果；可以绑定已支持的静态切片，但不支持 Copy 自身携带动态索引或部分区域复制。
- 新操作执行布局要求非零 rank，各维为大于 1 的静态二次幂；Fill 沿用原有与元素类型匹配的浮点常量填充接口。
- 保留每个连通分量最多 8 个变量、每个候选域最多 4 个候选的求解限制；执行证明的硬件坐标和逻辑点枚举各最多 65536 点，超限不会用抽样代替证明。
- 不包含一般跨过程别名证明、跨操作写竞争分析、完整 GPU lowering、TMA/cp.async、GEMM/Reduce 迁移或完整性能成本求解。

相对于 TileLang、Triton，当前可以强调的设计特点是：将存储与执行分开建模，将候选建议与硬正确性检查分开，并让选定结果在实际 IR 中可独立核验。不能据此宣称其他系统没有相关能力，也不能在未做上游运行差分和 GPU benchmark 的情况下宣称性能领先。

## 9. 可直接用于口头汇报的总结

> Task 19 完成了 Copy、Fill 和 Parallel 向统一布局推断体系的迁移。复制操作现在允许两端采用不同的存储顺序，但仍按逻辑元素一一对应；填充和复制明确规定由谁实际写入，避免多个持有者重复写同一个元素；并行区域的线程数则真正参与布局生成、筛选和验证。同时，编译器会检查向量访问是否连续、对齐且完整，将最终执行要求写回 IR，并重新核验。本阶段已通过既定回归测试，为后续 GEMM、Reduce 等操作迁移提供了基础，但尚不包含完整 GPU 指令生成或性能优化结论。
