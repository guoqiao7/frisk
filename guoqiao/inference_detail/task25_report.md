# Task 25 工作汇报：让 SM90 指令路径与真实地址参与布局选择

整理日期：2026-09-28。范围：M5 Task 25，采用已确认的方案 A。

本报告依据实际代码、测试用例及[实施计划](../layout_inference_implementation_plan.md) §25.4–25.5 整理。测试数字引用实现结束时的验收记录，本次编写报告未重新运行全量测试。

## 1. Task 25 解决什么问题？

Task 23 建立了有限候选搜索，Task 24 加入了共享转换与受限重计算的选择。Task 25 进一步补上目标硬件这一层：**一种布局不仅要合法，还要判断它能使用什么 SM90 指令路径，以及实际地址访问是否高效。**

例如，同样把一个矩阵块从 Global Memory 搬到 Shared Memory：

- 能否使用 TMA，取决于形状、类型、步长、对齐和 Shared 地址映射。
- 能否使用 cp.async，取决于每个线程的访问是否满足连续、对齐的分组要求。
- 即使三条路径都合法，也不能固定认为 TMA 最好；小块数据可能更适合普通向量搬运。

| 方面             | Task 25 之前                          | Task 25 新增或完善                                           |
| ---------------- | ------------------------------------- | ------------------------------------------------------------ |
| 目标信息         | 各目标规则已有能力判断                | 统一解析芯片、PTX 能力与设备属性，检查冲突                   |

## 2. 统一目标规则，并把已有 WGMMA 能力数据化

### 2.1 先确认硬件能力，不能靠猜

新增 `SM90TargetInfo`，统一读取 `frisk.target`、NVVM/GPU target，以及适用的 DLTI 设备信息。DLTI 可以理解为模块中声明的设备参数，例如 warp 大小。

具体例子：

```text
目标声明 sm_90a，且 PTX 能力满足要求
  → 可以继续检查 WGMMA 的类型、形状、布局契约

目标只声明 sm_90，或未显式声明 WGMMA 所需能力
  → 不能偷偷按 sm_90a 启用 WGMMA

目标声明 SM90，但适用设备信息声明 warp_size = 64
  → 与 SM90 的 32-thread warp 冲突，报错
```

没有显式 target 时仍可使用普通 SM90 布局环境，但这不等于默认获得 WGMMA 能力。

### 2.2 WGMMA 不是重新实现矩阵乘，而是统一已有契约

新增 `SM90InstructionTable`，将已有支持整理成 24 行规则：

```text
2 种输入类型：FP16 / BF16
× 2 种操作数模式：SS / RS
× 6 种 atom N：8、16、32、64、128、256
= 24 行

atom 形状：m64nNk16，FP32 累加
```

SS 表示 A、B 均来自 Shared；RS 表示 A 来自寄存器形式的 Tensor，B 来自 Shared。每个 warp-group 固定 128 个线程，整个 block 可以有多个 warp-group，当前支持 128/256/512/1024 个线程。

例如 FP16、SS、`m64n64k16` 可以命中规则表，但随后仍需证明 A/B 的真实 Shared 地址、major 方式和累加器 fragment 分配正确。**命中表项只是进入检查的条件，不等于跳过布局证明。**

这不是新增 CUDA Core 矩阵乘，也没有扩展 TF32/I8 路径；主要变化是让已有 Tensor Core 能力具备统一、可维护的规则入口。

## 3. 核心例子：同一个 Copy，怎样决定使用 TMA 还是普通向量？

### 3.1 输入条件

以测试中的静态整块 Copy 为例，下面是说明语义的伪代码：

```text
src : Global memref<32×64×f32>，根地址保证 128B 对齐
dst : Shared memref<32×64×f32>，根地址保证 1024B 对齐
copy(src, dst)

执行线程数：32
搬运数据量：32 × 64 × 4 = 8192 bytes
```

这里 128B/1024B 是该测试提供的对齐条件，不是所有 Copy 的统一要求。

### 3.2 第一步：联合准备布局和指令路径

一个 Copy 的候选由四部分组成：

```text
(源存储布局, 目标存储布局, 执行布局, 指令路径)
```

前两项回答“元素放在哪个地址”，执行布局回答“哪个线程、寄存器负责哪个元素”，指令路径回答“使用哪种搬运方式”。

即使前三项完全相同，TMA、cp.async、vector 仍是三个不同候选，不能因为布局相同而被去重成一个。求解器比较的是这些完整组合，不是先锁定布局、最后随意补一个指令名称。

### 3.3 第二步：先淘汰不合法的路径

| 路径          | 本阶段检查的主要条件                                                                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| TMA           | 静态 whole-tile Global→Shared；F16/BF16/F32；rank 1–5；box 每维 1–256；步长、对齐、swizzle 和实际地址满足契约 |
| cp.async      | Global→Shared；每线程存在已证明连续且对齐的 4/8/16B 分组；目标能力满足要求                                      |
| vector/scalar | 实际地址与线程分工满足访问、向量和写入者要求；从合法宽度中选择                                                   |

对上述 32×64 例子，存在满足条件的三类候选，可以进入成本比较。

如果改为“源、目标根地址只保证 1B 对齐”，测试中 TMA 和 cp.async 候选被删除，但普通 Copy 候选仍保留。这表示“当前证据不能证明快路径合法”，不是说整个 Copy 必须失败。

如果用户明确要求更宽向量，则必须满足该硬要求，不能用标量回退悄悄违背它。

### 3.4 第三步：按形状计算路径工作代理

对已证明每线程能连续访问 16B 的普通向量和 cp.async 候选：

```text
一个 warp 的一批访问覆盖：32 threads × 16B = 512B
8192B 数据需要：8192 / 512 = 16 批
```

当前模型使用以下静态评分：

| 路径     | 32×64 F32 的计算                | instructionPathAndWork |
| -------- | -------------------------------- | ---------------------: |
| 普通向量 | 16 批 load + 16 批 store         |                     32 |
| cp.async | 16 批搬运 + 2 单位固定工作       |                     18 |
| TMA      | 4 单位固定工作 + ceil(8192/1024) |                     12 |

因此，该测试最终选择 TMA。

这里的 4、2、1024 是版本化模型参数，分数是可解释的工作代理，**不是耗时、cycle，也不是保证生成的机器指令数**。

### 3.5 第四步：缩小数据块，选择就会改变

保持同类对齐条件，把形状改为 `8×16×f32`，只有 512B：

| 路径     | 8×16 F32 的计算                | instructionPathAndWork |
| -------- | ------------------------------- | ---------------------: |
| 普通向量 | 1 批 load + 1 批 store          |                      2 |
| cp.async | 1 批搬运 + 2 单位固定工作       |                      3 |
| TMA      | 4 单位固定工作 + ceil(512/1024) |                      5 |

这次三条路径仍都有合法候选，但求解器选择普通向量。

**这一变化体现了 Task 25 的作用：不是把 TMA 标成永远最优，而是让搬运规模与固定开销共同影响选择。** 上述两种最终路径都有实际求解、物化测试覆盖，不只是手算公式。

## 4. 地址不同，也会得到不同成本

九字段 `CostVector` 仍按字典序比较，不是把九项直接相加。Task 25 接通的前三项优先于第四项转换成本：

```text
instructionPathAndWork → memoryTransactions → bankConflictDegree
→ conversionBytesAndSync → 后续资源、复制、代码大小及稳定破同分项
```

所以第 3 节中第一项已分出优劣时，后面的 bank 分数不会反过来覆盖该决定。这是当前模型的优先级，不是实际 GPU 性能的普遍定律。

### 4.1 Global：连续访问与跨步访问不再同分

一个 warp 的 32 个线程，每个线程读取一个 F32：

| 实际访问方式              | 地址例子                   | 32B sector 数 |
| ------------------------- | -------------------------- | ------------: |
| 连续，首地址保证 32B 对齐 | 0、4、8、…、124           |             4 |
| 连续，但不能保证对齐相位  | 相同相对偏移，基址相位未知 |      保守取 5 |
| 每线程相隔 32B            | 0、32、64、…、992         |            32 |

求解器统计的是每个 warp/访问批次覆盖的实际 sector。未知对齐不能当作已经对齐，分别发生的访问也不能合并后少算。

这已经改变了一项实际回归的决策：同一个 Tensor 被两个不同存储布局的 store 使用时，现在可以选择**增加一次 warp 内 shuffle 转换，以减少 Global sector**。测试要求恰好一次 shuffle，并验证其 sector 数少于强制共用执行布局的方案。

在该比较中，第三项之前的访存成本能分出优劣，新增转换不会因为“转换数从 0 变为 1”就被机械拒绝。这将 Task 24 的边界修复能力与 Task 25 的地址评分接在了一起。

### 4.2 Shared：区分真正的 bank 冲突与读取广播

SM90 模型使用 32 个 bank、每个 word 4B，并在各个独立访问阶段内计分：

- 32 个线程读取同一个 word：按广播处理，冲突代理为 0。
- 32 个线程读取同一个 bank 中的 32 个不同 word：冲突代理为 `32−1=31`。
- 每个线程读取连续 16B：一个 warp 共 512B，分成四个独立 128B 阶段；连续访问各阶段均无冲突，不能把它误算成 4 路 bank conflict。

因此，不能只看“多少线程访问同一个 bank”；还必须看是不是同一个 word，以及这些访问是否属于同一阶段。该评分是带宽冲突代理，写入安全仍由地址和 ownership 证明负责。

## 5. 非二次幂形状：3×5 Copy 如何保证不越界？

Task 25 新增静态 guarded whole-tile Copy。以 `memref<3×5×f32>` 为例：

```text
实际逻辑形状：3×5，共 15 个有效元素
执行映射使用的载体形状：4×8，共 32 个坐标
有效条件：row < 3 && col < 5
```

可以把载体理解成“为二进制布局映射准备的规则坐标范围”，不等于实际分配了更大的数组：

```text
        col 0 1 2 3 4 5 6 7
row 0       ✓ ✓ ✓ ✓ ✓ × × ×
row 1       ✓ ✓ ✓ ✓ ✓ × × ×
row 2       ✓ ✓ ✓ ✓ ✓ × × ×
row 3       × × × × × × × ×
```

15 个有效点各有唯一选定的写入者，另外 17 个点不产生内存访问地址。源、目标仍是 3×5，不能把尾部屏蔽解释为允许访问填充区域。

输出契约保存 `valid_shape=[3,5]`、`guarded=true`。第一版只走标量路径，`vector_bytes=1` 是无宽向量要求的标记，不表示把 F32 元素拆成 1 字节读写。

目前只支持静态整块 Copy，不扩展动态形状、部分 Copy、ragged Fill 或 ragged MMA；逻辑域与载体域均受 65536 点证明预算限制。

## 6. 选中的方案不是一句标签，而是可复验的契约

选定路径后，在 Copy 上物化 `frisk.copy_contract`，记录：

- 路径、目标、向量宽度、有效形状与 guard。
- 发起方式和完成义务，例如 TMA 的 elected CTA thread、mbarrier 与 async-proxy 要求。
- 对 TMA，额外记录 box、Global strides、源/目标偏移、swizzle 和 interleave 模式。

验证器会从实际 SSA、存储地址、执行布局和目标信息重新推导，而不是相信“这个属性写了 tma，所以它就是合法 TMA”。例如，手动篡改 descriptor offset、删除 guard 或改写完成义务，都会被拒绝。

整个过程延续事务式物化：在临时模块上改写并复验，成功后才替换原模块；失败不留下半成品。

**当前交付的是布局与指令契约。记录 mbarrier/async-proxy 义务，不等于已经生成对应硬件同步或完成完整异步 GPU lowering。**

## 8. 可直接用于汇报的总结

> Task 25 把 SM90 目标能力、指令路径和真实访存地址接入了布局推断。现在 Copy 会联合选择存储布局、线程分工及 TMA/cp.async/普通向量路径：先证明合法，再按静态成本比较，因而大块数据和小块数据可以得到不同选择。同时，系统能分析 Global sector 和 Shared bank 冲突，支持带尾部屏蔽的静态非二次幂 Copy，并对实际 IR 中的契约重新验证。其特点是把存储、执行和指令关系放进同一套可核验的选择流程，而不是单独增加一个 TMA 特判；当前尚不代表完整 GPU 异步 lowering 或实测性能结论。
