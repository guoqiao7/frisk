# Task 24 工作汇报：联合选择布局转换位置与受限重计算

整理日期：2026-09-27。范围：M5 Task 24，采用已确认的方案 A。

本报告依据实际代码与[实施计划](../layout_inference_implementation_plan.md) §24.7 的验收记录整理。测试数字引用实现结束时的验收结果，本次编写报告未重新运行全量测试。

## 1. 一句话概括

Task 24 让布局求解器不只决定“每个位置用什么布局”，还一起决定“布局不一致时，是转换一次供多人共用，还是在使用处按目标布局重新计算”。这些方案在修改程序之前就参与成本比较，选中后再验证并写入 IR。

这里的“布局不一致”，是同一个 Tensor 的元素在线程、寄存器中的分配方式不同，不是 Tensor 数值发生变化。

## 2. 相比 Task 23，新增了什么？

| 问题                               | Task 23                                              | Task 24                                                   |
| ---------------------------------- | ---------------------------------------------------- | --------------------------------------------------------- |
| 如何选择布局？                     | 在有限候选中进行 exact/beam 搜索，以 CostVector 评分 | 保留搜索框架，将边界处理方案的成本纳入完整布局赋值的评分  |
| 多个使用者需要同一种转换怎么办？   | 按消费边处理转换，尚未联合选择共享位置               | 同源、同目标布局、同一基本块的使用者可以共用一次转换      |
| 生产者很便宜，是否一定搬运其结果？ | 没有本次受限重计算选择                               | 可以克隆便宜的纯计算，直接生成目标布局的结果              |
| 不同转换是否一样贵？               | 使用 CTA Shared 暂存的保守估计                       | 尝试区分线程内、warp 内和跨 warp 交换；无法证明时保守回退 |
| 如何落实选择？                     | 插入消费边转换并复验                                 | 显式记录位置、共享关系、重计算切片，核验后事务式物化      |

Task 23 已经支持“主计算收益能够胜过新增转换成本”。Task 24 不是首次引入这个原则，新增的是共享转换、重计算及其成本与位置的联合选择。

## 3. 例子一：两个使用者共用一次转换

考虑一个包含 64 个 f32 元素的 Tensor，由一个 warp 的 32 个线程持有，每个线程两个元素。两种布局都不复制数据：

| 线程 | 布局 A 持有的元素 | 布局 B 持有的元素 |
| ---- | ----------------- | ----------------- |
| 0    | x[0]、x[1]        | x[0]、x[32]       |
| 1    | x[2]、x[3]        | x[1]、x[33]       |
| …   | …                | …                |
| 31   | x[62]、x[63]      | x[31]、x[63]      |

假设 `%x` 已经是布局 A，而同一个基本块中的两个操作都需要按布局 B 使用它。下文是说明布局关系的伪代码，不是完整 MLIR。

Task 23 按两个消费位置分别处理：

```text
x : Tensor<64xf32, A>
b0 = convert_layout(x, A → B)
consumer0(b0)
b1 = convert_layout(x, A → B)
consumer1(b1)
```

Task 24 可以选择：

```text
x : Tensor<64xf32, A>
b = convert_layout(x, A → B)  // 放在最早的使用者前
consumer0(b)
consumer1(b)                  // 直接使用同一个转换结果
```

区别不是单纯把两条记录合并：实际 IR 中只有一个转换操作，两个使用者的操作数指向同一个 SSA 值。

这组布局的交换可以在同一个 warp 内完成。按 Task 24 的静态模型：

```text
源、目标各有 64 个物理元素槽，每个 f32 为 4 bytes
一次转换的搬运代理 = (64 + 64) × 4 = 512
warp 内交换的 CTA barrier 计数 = 0

分别转换两次：512 + 512 = 1024
共享转换一次：512
```

这里为了单独展示共享收益，使用的是同一套 Task 24 评分。Task 23 对这条路径使用更保守的暂存估计，不能把上述 1024 误认为它当时的实际评分。

共享要求源值相同、目标布局相同、使用者处于同一基本块，并且源值在插入位置已经可用。两个 `if` 分支中的使用者不会在本任务中被合并成分支外的一次转换。

## 4. 例子二：与其搬运常量，不如按目标布局生成一份

假设程序生成全为 3.0 的 Tensor，既有需要布局 A 的使用者，也有需要布局 B 的使用者。常量本身没有被硬约束锁死为某种编码。

原来的处理方式可以是：

```text
cA = constant(3.0), layout=A
consumerA(cA)
cB = convert_layout(cA, A → B)
consumerB(cB)
```

Task 24 可以选择：

```text
cA = constant(3.0), layout=A
consumerA(cA)
cB = constant(3.0), layout=B   // 在 consumerB 前克隆常量
consumerB(cB)
```

第二种方案不需要交换 `cA` 的元素，每个线程直接按 B 的分工产生所需常量。这就是 **rematerialization，受限重计算**。原来的 `cA` 和它的其他使用者保留不变，并不是把原常量的布局强行改成 B。

沿用上面的 64 元素例子：

```text
转换成本：512
克隆一个常量的工作代理：64 × 4 = 256
```

重计算成本更低，因此可以替代这条消费边的转换。256 是统一比较尺度，不表示执行了 256 条指令，也不是实际 GPU 耗时。

### 为什么不会给每个使用者都重算一遍？

如果同一块内有两个 B 使用者：

```text
分别克隆两个常量：256 + 256 = 512
共享一个转换：512
```

边界工作相同时，还会比较额外寄存器、复制与代码大小等字段；在这个测试场景中，共享转换胜出。完全同分时也保守地选择不克隆。

因此，“单个使用者适合重算”不等于“多个使用者各自重算仍然划算”。Task 24 会把共享收益一起考虑。目前不共享新克隆的计算结果，不能把这个例子扩大解释为所有可能改写中的最优方案。

### 算术表达式也能重算，但输入转换不能漏算

例如 `y = a + b` 的原结果是布局 A，某个使用者需要 B：

- 如果 `a`、`b` 已经可以按 B 使用，就有机会在该使用者前克隆一次加法，直接得到 B 布局的 `y`。
- 如果必须先把 `a`、`b` 转为 B，这些输入转换也要计费；总成本可能超过直接转换 `y`，此时不选择重算。
- 同一个外部输入在重计算切片中被多次使用，只转换一次，不重复生成或收费。

实现检查的是整个被克隆的生产依赖片段，而不只是最后一条加法。

## 5. 重计算有什么安全限制？

不是所有“看起来可以再算一次”的操作都能复制。

当前只支持 dense Tensor 常量、逐元素浮点/整数加减乘、整数按位与/或/异或及 `select`，并要求操作接口能证明没有副作用。操作必须无 region、单 Tensor 结果，相关 Tensor 满足静态同形等要求。

此外还有限制：

- 一个向前追溯生产依赖的切片最多包含 **8 个不同操作**；共享子表达式只算一次，出现第 9 个操作则不提供这条重计算候选。
- 只克隆使用者所在基本块内的操作。块参数、不支持复制的操作结果以及跨块输入可以作为外部输入，但不继续跨块复制其生产者。
- 所有外部输入与标量依赖必须在插入位置可用；克隆保留属性与运算顺序，不进行浮点重结合。
- 每个克隆结果都要满足目标布局、硬编码要求和资源限制，不能绕过 SameLayout、AliasLayout、MMA、Reduce 或 Storage 契约。
- load/store、MMA、Reduce、随机、时钟、除法、未知操作以及 `tensor.empty` 不在克隆白名单内。

例如，循环体内生成的常量可以在循环体内重算；但即使循环外的生产者是纯操作，也不会被本任务复制进循环。循环携带值原有的布局关系同样保持不变。

## 6. 成本估计比以前细在哪里？

### 6.1 根据元素归属区分交换范围

对支持分析的布局，检查“目标线程要的元素，源布局中的哪个线程持有”：

| 分类         | 含义                                       | 当前估计                                   |
| ------------ | ------------------------------------------ | ------------------------------------------ |
| Register     | 目标线程自己就持有需要的源元素             | 按目标物理元素槽计工作，无 CTA barrier     |
| Shuffle      | 需要其他线程的元素，但同一 warp 内可以取得 | 按源、目标物理元素槽计工作，无 CTA barrier |
| Shared       | 需要跨 warp 获取元素                       | 搬运代理加 2 次同步惩罚                    |
| Conservative | 当前布局或预算不支持完成分类证明           | 保留 CTA 暂存的非零保守估计，并标记来源    |

存在数据副本时，只要当前线程或当前 warp 已有可用副本，就不必按更大通信范围估计。相同编码无需修复，成本为零；不能因为某条未知路径分析不出来，就把它当作免费。

分类只在有限支持域中进行，包括可规范化的 BitLinear 映射、lane=32、相同活跃线程 topology。最多检查 65536 个逻辑元素、两端合计 262144 个物理元素槽，超出时回退，避免分析本身失控。这些分类用于成本估计，不意味着本任务已经生成对应 CUDA 指令。

### 6.2 把转换与重计算放在同一层比较

九字段 CostVector 仍按字典序比较，不是把所有字段加成一个总分。Task 24 将第四项 `conversionBytesAndSync` 明确为“边界修复成本”：既可以是转换搬运与同步，也可以是克隆计算与必要输入转换。

这样不会因为把克隆工作单独塞进更高优先级的主计算字段，而机械地禁止所有重计算。目标模型对原程序主计算路径的评分优先级保持不变；克隆产生的额外寄存器槽、复制与代码大小也计费。

对于循环内的边界修复，第四项乘以 `2^循环嵌套深度`，采用饱和运算防止溢出。它只是表达“重复执行的位置值得更重视”的静态代理，不是实际循环次数；代码大小等静态资源不随这个权重成倍增加。

当前 SM90 模型的主计算、访存事务、bank conflict 前三项仍未完成硬件建模，不能将静态评分直接解释成真实性能。

## 7. 不是事后修补：先参与选择，再验证、写入程序

处理过程是：

```text
已有有限布局候选与硬约束
  → exact/beam 产生完整布局赋值
  → 按“同源、同目标、同块”比较共享转换与各使用者的独立方案
  → 将边界成本加入赋值评分，选择完整方案
  → 验证转换位置、共享关系、克隆切片及成本记录
  → 在临时模块中物化，复验实际 IR，成功后替换原模块
```

生产与消费布局相同时，直接保持共同布局，不生成边界修复操作。已经存在的显式转换保留原位置并计费，不重复插入。

每个布局不一致的实际使用位置仍保留一条边界记录，共享转换的记录通过同一个 leader 关联。因此，分析输出中有两条边界记录，不一定代表最后生成了两个转换操作。

验证器会从原始 SSA、布局赋值与硬约束重建计划，检查插入点、共享关系、切片和成本元数据。物化在临时模块中进行，随后执行 MLIR 验证与实际布局复验；方案被篡改或任一步失败，都不会把部分修改留在原模块中。

搜索仍有预算，beam 仍可能截断。这里的联合选择是在有限候选、同块分组和受限重计算模型内完成的，不保证任意跨 region 改写的全局最优。
