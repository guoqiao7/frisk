# Task 18 工作汇报：让布局推断正确理解切片与循环

范围：M4 第一阶段的 Task 18，不代表整个 M4 已完成。

## 1. 概括

布局推断要回答两个问题：数据在内存里怎么放，以及张量元素由哪些 GPU 线程和寄存器持有。

M3 已经能为一部分张量程序补齐布局，并处理 `if`、`for`、`while` 中的布局传递。Task 18 在此基础上，重点补强了“同一块内存的不同视图”和“控制流中的布局关系”：

- 对切片，能根据偏移、步长等信息计算其真实布局，检查它与其他视图是否冲突。
- 对循环和分支，明确记录布局从哪里传到哪里，哪些必须一致、哪些可以通过转换衔接。
- 对推断过程，先准备有限候选，再不断排除不合适的方案，并记录可以核对的收敛统计。
- 对最终结果，重新检查实际生成的程序；验证失败时，不留下改写一半的程序。

本阶段的主要成果是提高布局推断的正确性、可解释性和可验证性，不是新增一种矩阵乘法算法，也不是已经证明 GPU 性能提升。

## 2. 能理解“不同视图，其实指向同一块内存”

### 2.1 解决什么问题

把一个矩阵切出一部分，通常不需要重新分配内存。切片只是换了一套坐标，访问原来那块内存中的部分元素。

例如，原矩阵中的 `A[1,2]`，可能就是切片中的 `B[0,0]`。两者名字和坐标不同，但指向同一个元素，这就是这里的“别名关系”。

因此，不能简单要求 A、B 使用完全相同的布局公式，也不能把 A 的公式原样复制给 B；必须先弄清楚坐标之间的对应关系。

### 2.2 具体例子：带偏移、带步长的切片

假设 A 是一个按行存储的 `4×8` 整数矩阵，每个元素占 4 字节。取下面的切片，索引从 0 开始：

```text
B = A[1:3, 2:8:2]

含义：选第 1、2 行，以及第 2、4、6 列。

B = [ A[1,2]  A[1,4]  A[1,6] ]
    [ A[2,2]  A[2,4]  A[2,6] ]
```

A 每行占 `8×4=32` 字节，因此：

```text
A[r,c] 的字节偏移 = 32r + 4c
B[i,j] 对应 A[i+1, 2j+2]
B[i,j] 的字节偏移 = 32(i+1) + 4(2j+2)
                     = 32i + 8j + 40
```

这些偏移都相对于同一个底层内存起点。B 的六个元素实际位于：

```text
[ 40  48  56 ]
[ 72  80  88 ]  字节
```

Task 18 已经能推导并验证这种关系。A 和 B 的布局公式不同，但 `A[1,2]` 与 `B[0,0]` 都落在第 40 字节，因此是一致的。

这里的 `layout_view` 只是给内存视图绑定布局描述，不会分配新内存，也不会把数据搬到另一处。

### 2.3 不只是推导，还会发现错误

现在会检查三类问题：

- 同一个元素不能有两个地址。例如另一个视图也访问 `A[1,2]`，却声明它在第 44 字节，会被拒绝。
- 不同元素不能意外占用同一段空间。例如把 `A[1,4]` 也放在第 40 字节，会与 `A[1,2]` 冲突。
- 不能越出底层内存的可访问范围。本例 A 占 128 字节，B 最后一个元素占据 `[88,92)`，在合法范围内。

对同一底层存储上的实际布局视图，会检查所有视图对，而不是只检查相邻的两个，避免漏掉“第一个与第三个冲突”的情况。对于不足一个字节的元素，检查精确到位区间。

本阶段支持能静态证明的同元素类型、同内存空间的 `memref.cast` 和 `memref.subview`，包括非零偏移、正步长、降维和嵌套切片。

## 3. 能为切片准备候选，但不会凭空猜出整个矩阵

布局推断不是无限尝试所有可能的排布，而是先准备有限的候选方案。

候选主要来自三处：程序显式指定的布局、目标模型提供的有限默认模板，以及沿已支持关系推导出来的布局。显式指定的布局还会形成硬性要求，不能为了求解方便偷偷换掉。

### 3.1 已知整体，可以推导局部

上一节已知 A 的布局，便可以把切片坐标代入，得到 B 的布局。对支持的 XOR 布局，也已经实现了考虑整数偏移和进位的精确投影。

例如，一个四元素数组，每个元素占 1 字节，逻辑位置 `0、1、2、3` 经过一种 XOR 排布后，实际字节位置是：

```text
原数组： [0, 1, 3, 2]
取后 3 个逻辑元素后的切片：[1, 3, 2]
```

切片偏移必须按整数加法处理，不能直接当作 XOR：`1+1=2`，而 `1 XOR 1=0`。Task 18 对这类情况做了专门处理和测试。

投影也会重新检查向量访问保证。例如，原数组支持连续 16 字节的向量块，不意味着“从第 1 字节开始的切片”仍支持相同的向量访问。推断生成的候选会在必要时降低向量粒度；程序显式要求的不合法保证则会报错。

### 3.2 只知道局部，不能唯一确定整体

仍以每个元素占 1 字节为例，假设只知道 A 的前两个元素在字节位置 0、1。那么以下两种整体布局都可能成立：

```text
整体方案一：[0, 1, 2, 3]
整体方案二：[0, 1, 3, 2]
```

切片没有告诉我们后两个元素怎么放，因此不能通过“反推切片”声称已经获得唯一的整体布局。

当前实现会用切片信息筛选已有的整体候选，不会凭空补出未被观察到的部分。只有目标视图完全位于已知视图覆盖的范围内、坐标对应又唯一时，才允许进一步转移布局信息。

这项工作的价值是：既能利用局部信息，又不把局部信息误当作全局证明。

## 4. 能清楚表达循环中的布局传递关系

### 4.1 “图”是什么

这里的图是编译器内部的一张关系网：节点代表需要确定布局的对象，边代表对象之间必须满足的关系。

Task 18 新增了显式的区域布局边，记录分支出口、循环入口、循环回边等位置的流向、所属操作和参数位置，并关联已有约束。它没有另造一套循环求解规则，而是把 M3 已有的语义明确记录下来，便于检查和追踪。

理解下面三种关系，就能读懂最常见的情况：

| 关系            | 通俗解释                                                   | 典型场景                                |
| --------------- | ---------------------------------------------------------- | --------------------------------------- |
| `AliasLayout` | 指向同一存储的视图，对同一元素的地址必须一致；公式可以不同 | 原矩阵与切片                            |
| `SameLayout`  | 布局编码必须相同                                           | `for` 的迭代参数与循环结果            |
| `Convertible` | 布局允许不同，但必须能在具体使用位置显式转换               | 循环初值进入循环、计算结果交给`yield` |

这三种关系都已实现并用于当前推断流程，但不是都在 Task 18 中首次引入。Task 18 重点增强了别名关系及区域边的记录与核验。

### 4.2 具体例子：一个累加循环

先看不带布局的伪代码，其中加法表示向量逐元素相加：

```text
acc = [0, 0, 0, 0]
for i in range(3):
    acc = acc + [1, 1, 1, 1]
result = acc
```

在编译器的 `scf.for` 中，`acc` 对应迭代参数 `iter_arg`：它是“这一轮带进来的累计值”，不是循环下标 `i`。循环体通过 `yield` 交出更新后的值，供下一轮或最终结果使用。

假设循环状态采用布局 L2，而原始初值、循环体某个计算结果分别采用 L1、L3，布局关系可以理解为：

```text
初值 L1 ──必要时转换──> acc L2
                         │
                     循环体计算
                         ↓
                   下一值 L3
                         │
                    必要时转换
                         ↓
                      yield L2
                         │
                  ┌──────┴──────┐
                  ↓             ↓
              下一轮 acc L2   最终 result L2
```

这里 L1/L2/L3 只是说明边界转换的示意，不表示一次普通加法必然改变布局；若两侧本来相同，就不需要转换。

为什么 `acc` 和 `result` 必须保持 `SameLayout`？因为当前 `scf.for` 把它们作为同一个循环携带状态的输入、输出类型，布局编码又是张量类型的一部分。`yield` 交出的值无论进入下一轮还是成为最终结果，都要符合这套类型；循环出口没有自动更换布局的隐含动作。

如果外面的消费者需要 L3，可以在循环结果之后显式转换，而不是让循环内部的状态类型不一致。

对于 `if`，记录各分支交给结果的布局关系；对于 `while`，分别处理进入条件区域和条件转发到循环体/结果的两组值，不强行把不同数量、不同类型的两组参数逐项绑成相同布局。

## 5. 能逐步排除不合适的布局，并说明何时停止

候选准备完成后，候选集合被冻结。后续传播只删除不合适的方案，不再一边删除、一边不断添加新方案。

可以把它理解为“先列出备选项，再根据条件逐项排除”。例如三个对象要求相同布局：

```text
A 的候选：{L1, L2, L3}
B 的候选：{L2, L3, L4}
C 的候选：{L3, L4, L5}

要求：A 与 B 相同，B 与 C 相同。
```

先检查 A、B，可以删掉各自不共有的候选；再检查 B、C，会发现 B 只能保留 L3；B 的变化又通知 A，最终三者都只剩 L3。

这里可以核对：初始有 9 个候选，最终剩 3 个，一共删除 6 个。这类多轮筛选已经有单元测试覆盖。

实现上使用待处理队列：只有某个对象的候选真的变少，才重新安排与它有关的约束检查。队列中的重复任务会去重，并记录候选删除数、集合变化次数、队列处理次数等统计，检查它们是否符合推导出的上界。

由于候选有限且只减不增，这一删减过程能够终止。队列为空表示“继续应用这些规则也不会再删候选”，不一定意味着只剩唯一方案，更不意味着已经找到性能最优方案；后续仍需完成求解和核验。
