# Task 23 工作汇报：从小图临时求解到有预算、有成本的布局选择

整理日期：2026-09-27。范围：M5 Task 23，采用已确认的方案 A。

本报告依据现有代码和[实施计划 §23 的验收记录](../layout_inference_implementation_plan.md#task-23-实现连通分量候选求解和-costvector)整理。测试数字引用 Task 23 实施结束时的实际结果，本次编写报告未重新运行全量测试。

## 1. 一句话概括

Task 23 将原来“只能处理小图、主要比较转换次数”的临时布局求解器，替换为“按约束联合选择布局、按成本比较方案、按预算控制搜索”的正式求解器，并使此前受规模限制的完整 MMA→Reduce→Global 写回链成功通过布局推断。

它与前面几个任务的分工是：

- Task 19–21：定义 Copy、Parallel、MMA、Reduce 等操作需要满足的布局关系与证明规则。
- Task 22：让受支持的旧 Buffer 程序转换为新 Tensor 程序，并提供可验证、可回滚的统一流水线。
- Task 23：在这些操作允许的有限布局候选中，选择一组彼此兼容、成本较低的方案。

这里不是新增矩阵乘或归约算法，也不是首次引入联合求解。此前的临时求解器已经会对小连通分量联合枚举；本次升级的是求解规模控制、选择依据、确定性与完整链验收。

## 2. 相比 Task 23 之前，具体改变了什么？

下表的“之前”指 Task 22 结束时的新体系临时求解器，不是更早的旧 `layoutMap` 推断路径。

| 对比项   | Task 23 之前                                                   | Task 23 之后                                                       |
| -------- | -------------------------------------------------------------- | ------------------------------------------------------------------ |
| 规模控制 | 每个连通分量最多 8 个变量，每个变量最多 4 个候选，超限直接失败 | 移除这两个通用限制，按候选组合数选择搜索方式，并限制实际搜索工作量 |
| 搜索方式 | 小图深度优先穷举                                               | 小组件精确搜索，大组件确定性 beam search                           |
| 方案评分 | 优先减少新增布局转换次数                                       | 接通九字段 CostVector，再以完整稳定编码标识解决同分                |
| 转换成本 | 有 bytes/sync 字段，但求解时未填充                             | 计算静态搬运与同步估计，已有转换也计费，但不重复插入               |
| 失败说明 | 包括“变量太多”“候选太多”                                   | 区分硬约束未被证明、截断后未找到解、搜索预算耗尽                   |
| 完整链   | MMA→Reduce→store 的 9 变量核心超限                           | 核心链以及含 Copy、Parallel128 的更完整链均通过                    |

MMA、Reduce 等操作自身的候选证明预算没有放宽。通用求解器能接受更多变量，不代表目标硬件支持集、数值语义或操作证明能力也随之扩大。

## 3. 如何在更大的图中选布局？

### 3.1 把必须一起考虑的布局放在一起求解

“布局变量”就是一个需要确定布局的位置，例如 Tensor 的生产位置、某个操作的消费位置，或者一个 MemRef 的存储布局。

这些位置通过硬约束相连。连在一起、不能独立决定的变量组成一个连通分量。例如：

```text
MMA 结果的生产布局
        ↓ Convertible：允许相同布局，或合法转换
Reduce 输入的消费布局
        ↓ ReductionLayout：输入与输出必须满足归约契约
Reduce 结果的生产布局
        ↓ Convertible
Store 输入的消费布局
        ↓ StorageAccess：线程持有的元素必须写到对应地址
Global 输出的存储布局
```

求解器不能为了把图拆小，就忽略 Convertible 边或合并真实的生产、消费位置。选择一个布局时，还要检查 MMA 的整组角色、Reduce 的输入输出是否仍有相容的完整组合。

### 3.2 用组合数选择 exact 或 beam

先沿用已有候选准备与传播，再去重和检查硬要求。搜索开始后，候选域固定，不在搜索中临时创造新布局。

默认规则是：

```text
剪枝后的候选组合数 ≤ 256：exact，精确搜索
剪枝后的候选组合数 > 256：beam，每层最多保留 32 个部分方案
每个组件最多尝试 65536 次候选扩展
```

例如，假设一个组件中每个变量都还有两个候选：

- 8 个变量有 `2^8 = 256` 个原始候选组合，采用 exact。
- 9 个变量有 `2^9 = 512` 个原始候选组合，采用 beam，而不是仅因为变量数是 9 就拒绝。
- 如果硬要求已经把 9 个变量都固定成单一候选，组合数就是 1，仍采用 exact。

这个例子只解释模式选择，并不表示真实 MMA 链一定每个变量有两个候选。组合数还使用溢出安全计算，不能因整数溢出把大搜索空间误判为小图。

exact 会在预算允许的情况下穷尽合法方案；beam 则只保留当前排序靠前的部分方案，控制组合增长。beam 丢弃过分支后，即使找到解，也不保证它是最优解。

### 3.3 优先处理选择最少的位置

搜索每一步优先处理“当前可行候选最少”的变量；数量相同，再比较硬约束关联度和稳定 ID。直观上，就是先处理最受限制的位置，尽早发现冲突。

每次试探都计入预算，包括不合法的试探和用于比较剩余候选数量的试探。预算不是只统计最终留下的成功节点。

## 4. 如何比较两个合法方案？

### 4.1 接通 CostVector，但不把九项都说成已实现硬件模型

比较采用字典序：先比较第一项，只有相等才比较第二项，依此类推。它不是把九项随意加权求和。所有硬要求必须先满足，低成本不能让一个非法布局通过。

| 字段                        | Task 23 中的实际作用                                                |
| --------------------------- | ------------------------------------------------------------------- |
| `instructionPathAndWork`  | 通用引擎支持比较；SM90 首版未建模，保持中性                         |
| `memoryTransactions`      | 同上，尚不是访存事务数量预测                                        |
| `bankConflictDegree`      | 同上，尚不是 bank conflict 硬件模型                                 |
| `conversionBytesAndSync`  | 转换搬运量与同步惩罚的静态估计                                      |
| `spillRiskAndRegisters`   | 按计费定义位置或操作执行布局，累加每线程寄存器坐标槽数              |
| `sharedBytesAndOccupancy` | 按 Shared 底层存储根统计最大占用末端，同根别名只计一次              |
| `replication`             | 按计费定义累加`replication - 1`                                   |
| `codeSize`                | 首版统计已有和新增的非恒等转换操作数                                |
| `deterministicTieBreak`   | 通用比较接口保留此项；SM90 保持中性，最终同分由完整稳定赋值标识解决 |

寄存器槽数不是活跃寄存器峰值，Shared 占用也不是完整 occupancy 预测。前三项保持中性表示“尚未建模”，不是“实际没有开销”。

### 4.2 例子：更好的主计算可以胜过零转换

实际单元测试使用受控目标评分，构造两个合法选择：

```text
方案 A：生产布局与消费布局相同
        主计算代价 = 100，转换代价 = 0

方案 B：生产布局改用另一个合法编码，消费前做一次转换
        主计算代价 = 0，转换代价 = 768
```

新求解器选择 B，因为主计算字段比转换字段优先。旧临时求解器主要比较新增转换次数，会优先选择没有转换的 A。

这证明的是“主计算代价能够参与并主导方案选择”的引擎能力。这里的 100 和 0 是测试目标提供的评分，不是当前 SM90 模型对真实 MMA 的性能预测，也不是 GPU 实测结果。

同样，如果主计算成本相同，新求解器会比较转换搬运与同步成本，而不是把所有“一次转换”都看作等价。

### 4.3 例子：一次转换为什么得到 768？

在上述测试中，两种布局都覆盖 64 个 f32 物理槽，线程覆盖为 32：

```text
每元素字节数 b = 4
源、目标物理槽数 Psrc = Pdst = 64
搬运估计 bytes = b × (Psrc + Pdst) = 512
同步估计 sync = 2
转换评分 = bytes + 4 × T × sync
         = 512 + 4 × 32 × 2
         = 768
```

物理槽数由完整 topology 计算；存在复制时，它可能多于逻辑元素数。这一估计按单 CTA Shared 暂存路径计算写入和读取的保守搬运量，来源标记为 `cta-staging-upper-bound-v1`。

同一 CTA 内若两端覆盖不同活跃线程子集，例如 32→128，则同步项取 `T=max(Tsrc,Tdst)`，保留原有合法转换语义。相同编码转换成本为零；已有显式转换只计一次，不再插入一个重复转换。

768 是公开的静态比较尺度，不是时钟周期、纳秒或已经分配的 scratch 大小。

### 4.4 例子：同一块 Shared 的两个视图不能重复收费

假设两个合法子视图属于同一个 Shared 根，占用字节区间分别为：

```text
视图 A：[4,12)
视图 B：[20,28)
```

该根计费为从根原点到最大占用末端的 28 bytes，只计一次。它不是两个区间长度之和 16 bytes，也不是去掉开头空隙后的 24 bytes。不同根分别计费再相加。

类似地，同一个 Tensor 被多个操作消费，不会因为多建了几个消费位置变量，就把它的生产位置寄存器槽数重复累计。

## 5. 最直接的成果：完整计算链不再卡在 8 变量限制

### 5.1 先补齐原来的 9 变量核心

SS MMA→Reduce→Global store 的核心图包含：

```text
MMA：A Storage、B Storage、init 生产位置、init 消费位置、结果，共 5 个
Reduce：输入消费位置、结果，新增 2 个
Store：输入消费位置、输出 Storage，新增 2 个
合计：9 个连通变量
```

Task 21/22 时可以分别验证其中若干段，但完整核心超过临时求解器的 8 变量上限。Task 23 没有删掉某个节点来凑数，而是换掉规模控制方式，让这 9 个真实位置共同完成选择。

新的集成测试从受支持的旧程序出发，经过 normalization 和完整布局 pipeline，验证 MMA/Reduce 契约存在、输出确实连接外部 Global 参数、实际 IR 复验通过，并且重新运行结果不变。

### 5.2 完整例子：Copy→Parallel128→MMA→Reduce→Global 写回

以下伪代码对应实际集成测试的形状和操作，不是可直接粘贴的完整 MLIR：

```text
目标：SM90a
输入：Global A[64,16] f16，Global B[16,64] f16
输出：Global out[64] f32

分配 Shared As[64,16]、Bs[16,64]，提供测试要求的对齐

Parallel，128 线程：
    Copy(A, As)
    Copy(B, Bs)
    zero = 全零 Tensor[64,64] f32
    C = mma(As, Bs, zero)                  // Tensor[64,64] f32
    R = reduce_tensor(C, kind=sum, dim=1)  // Tensor[64] f32
    tile_store(R, out)
```

各任务在这个例子中的作用可以直接分开：

1. Task 19 规则约束两次 Copy 的线程分工、访问和写入责任，并落实 Parallel128 的执行范围。
2. Task 20 规则约束 Shared A/B、累加器和结果如何符合 MMA 指令要求。
3. Task 21 规则约束 C 到 R 的归约布局、贡献者与通信契约。
4. Task 23 把相连的位置一起求解，在合法候选中选择方案，并确定是否需要消费位置转换。
5. 既有物化与 Task 22 事务流水线把方案写入 IR，保存所需契约，再检查真实 IR。

该测试验证两次 Copy 的执行布局与 128 线程属性、MMA/Reduce binding、对外部输出参数的 store，以及序列化、重新解析、重跑后的稳定性。它直接使用新操作；另一个 9 变量核心测试覆盖旧程序 normalization 的入口。

因此，现在通过的是完整布局推断、物化与复验，不是仅把几个独立通过的测试拼成一条“假定成功”的链，也不等于已经生成并执行 GPU 内核。

## 6. 不只要能成功，还要把失败和结果解释清楚

搜索失败分成不同情况：

- 固定候选域穷尽后没有可证明的方案：报告没有可行的已证明赋值；不能扩大解释为任意可能布局都无解。
- beam 曾丢弃分支，剩下的分支未找到解：报告 `search-incomplete`，不能声称已经证明无解。
- 尝试次数达到上限：报告 `search-budget-exceeded`，不提交尚未完成的部分方案。

一个实际测试用例中，窄 beam 会丢掉唯一能够最终完成的分支；加宽 beam 后能够找到它。这验证了“搜索没找到”与“根本不存在”不能混为一谈。

将完整链的 `maxExpandedStates` 显式设为 1 时，另一个测试确认 pipeline 报预算不足，而且原模块保持不变。旧的 8 变量失败用例变成成功验收后，回滚覆盖仍然保留。

确定性方面，候选按完整结构身份去重并稳定排序，不把插入序号当作性能偏好。即使数学映射类似，维度名称、topology 或 replication 不同，也不能随意当作相同 SSA 编码合并。成本同分时使用完整稳定赋值标识，不依赖内存地址或哈希表遍历顺序。

`dump-analysis` 还能输出组件搜索模式、候选组合数、域大小、尝试数、硬拒绝数、beam 丢弃数、是否穷尽、CostVector 和转换 bytes/sync。数值计算发生溢出时采取饱和而非回绕，并记录相应标志。

## 8. 汇报时应保留的边界

Task 23 完成的是有限候选范围内的有界选择，不是无限搜索任意布局。beam 截断后不承诺最优；组件独立最优也不能无条件推广为饱和总成本的全局最优。

本任务没有扩展 MMA/Reduce 的操作证明预算，没有完成转换提升、重计算或关键路径调度，也没有完成完整 SM90 性能模型。这些仍属于后续任务。当前成本是静态比较依据，不能由此宣称比 TileLang、Triton 更快，或宣称 GPU 性能已经提升。

可直接用于汇报的总结：

> Task 23 把新 Frisk 的布局选择从受 8/4 规模限制的临时求解器，升级为有界 exact/beam 与 CostVector 驱动的正式求解器。它保持已有硬约束和独立复验，新增可审计的成本与搜索统计，并使 Copy、MMA、Reduce 到外部 Global 写回的完整链真正通过布局推断。当前交付是更完整、可解释的布局选择能力，而不是 GPU 性能结论。
