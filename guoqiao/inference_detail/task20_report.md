# Task 20 工作汇报：让矩阵乘法接入统一布局推断与指令契约验证

整理日期：2026-09-19。范围：M4 第三阶段中的 Task 20；不代表整个 M4 已完成。

## 1. 一句话概括

Task 20 让 Frisk 能够为受支持的矩阵乘法，联合确定“输入在共享内存中怎么放、寄存器中的元素怎么分、线程组怎么组织”，并检查这些布局是否真正符合 SM90a 矩阵指令的要求。

它不是只给矩阵乘法附加一个布局标签，而是打通了：

```text
表达矩阵乘法 → 收集布局要求 → 准备有限方案 → 联合筛选与求解
                                                     ↓
               成功后更新程序 ← 独立复验 ← 写入临时 IR
```

这里的 IR 是编译器内部表示。此次交付的是布局推断、结果写入和静态正确性验证，尚未生成完整 GPU 矩阵乘法内核，也没有性能提升结论。

前几个任务与本任务的关系可以概括为：

- Task 18：明确不同视图是否指向同一块存储，以及布局如何经过循环和分支传播。
- Task 19：让 Copy、Fill、Parallel 明确数据访问、线程分工和写入责任。
- Task 20：让矩阵乘法的多个输入、累加器和硬件指令要求形成一套相互匹配的布局方案。

## 2. 新增 `frisk.mma`，明确表达矩阵乘加

MMA 是“矩阵乘加”。新操作的数学含义是：

```text
result = init + A_eff × B_eff
```

其中 A_eff、B_eff 是根据转置属性解释后的逻辑矩阵；init 是已有累加值，result 是新结果。没有转置时，就是 `result = init + A × B`。

这次的重要调整是：累加器和结果使用 Tensor SSA 值表达，而不再为新路径使用 Local MemRef 模拟寄存器片段。可以把 SSA 理解为“操作产生一个新的值”，不是暗中覆盖某块累加器内存。

### 2.1 具体例子：计算一个 `128×128` 的结果块

假设输入如下：

| 对象   | 形状和类型               | 含义           |
| ------ | ------------------------ | -------------- |
| A      | `128×64`，bf16        | 左矩阵         |
| B      | `64×128`，bf16        | 右矩阵         |
| init   | `128×128`，f32 Tensor | 已有累加值     |
| result | `128×128`，f32 Tensor | 乘加后的新结果 |

每个结果元素的数学关系为：

```text
result[i,j] = init[i,j] + Σ A[i,k] × B[k,j]，k = 0…63
```

如果是第一次计算，就给 init 传入显式零 Tensor；如果是继续累加，就传入之前的结果。不能用“尚未初始化的空 Tensor”代替零。

编译器会先检查形状、类型和转置关系。例如，把存储为 `64×128` 的 A 当作有效的 `128×64` 左矩阵使用，需要正确设置逻辑转置；不能只因为元素总数相同就接受。

数学表达不额外承诺某种浮点求和顺序。当前目标支持 f16/bf16 输入与 f32 累加，不能把它与旧 f16 累加测试视为已经完成数值等价验证。

### 2.2 支持两种输入组织：SS 和 RS

| 路径 | A 从哪里来             | B 从哪里来      | init/result |
| ---- | ---------------------- | --------------- | ----------- |
| SS   | Shared 共享内存        | Shared 共享内存 | Tensor      |
| RS   | Tensor，表达寄存器片段 | Shared 共享内存 | Tensor      |

Shared 输入通过 `layout_view` 绑定存储布局。RS 则允许 A 已经由前面的 Tensor 计算产生，随后按矩阵指令所需的寄存器分布消费。

本阶段不支持寄存器形式的 B，也不会偷偷分配 shared buffer，把不支持的输入改造成另一种路径。MemRef 输入只读，不隐含修改 A/B、写回输出或清零。

## 3. 不是“分别合法”就够了：四个角色必须联合匹配

矩阵乘法对布局的要求具有配套关系。例如，A 的寄存器分配、B 的 shared 地址解释、累加器的分布和线程组组织，必须属于同一种可执行的指令方案。

可以把它理解为组装设备：每个零件单独合格，不代表随意挑选后就能装在一起。

Task 20 将一次 MMA 的四个角色按固定顺序关联：

```text
[A 消费位置，B 消费位置，init 消费位置，result]
                         ↓
             一条联合 InstructionContract
```

`InstructionContract` 的含义是“指令布局契约”。内部保存有限的合法组合，每个组合同时包含四个角色的布局和一个完整指令方案；不是把四个角色各自检查通过后就结束。

### 3.1 一个简化例子

下面只是解释联合约束的示意表，不代表实际 SM90 候选的具体数量或编码：

| 完整合法方案 | A 布局 | B 布局 | init 消费布局 | result 布局 |
| ------------ | ------ | ------ | ------------- | ----------- |
| 方案一       | A1     | B1     | C1            | C1          |
| 方案二       | A2     | B2     | C2            | C2          |

虽然 A1、B2 都分别出现在合法方案中，但不能据此认为 `A1 + B2 + C1 + C1` 合法；表中没有任何完整方案支持这一组合。

如果其他约束已经排除了 B1，那么方案一也失去支持，A1 就不能继续作为这条指令的可选布局保留。即使还没有哪个变量只剩一个候选，联合约束也会执行这种筛选。

对应到实际实现：

1. 先收集显式布局与目标模型允许的有限建议。
2. 候选集合冻结后，传播阶段只删除没有完整组合支持的候选，不无限生成新布局。
3. 求解每选择一部分布局，都检查是否还能扩展成同一条完整合法组合。
4. 最终选定的是四角色布局加对应指令方案，而不是四个互不相关的答案。

这使 Task 18 的有限候选传播，从常见的两端关系扩展到了真正的多角色联合关系。当前仍保留每个连通分量最多 8 个变量、每个候选域最多 4 个候选的限制；四角色契约最多检查 `4⁴=256` 个编码组合，超限明确报错，不静默截断。

## 4. 能检查“元素覆盖正确，但指令仍然不能用”的布局

普通布局检查回答的是：每个逻辑元素是否都有持有者，是否越界，重复持有是否符合约定。

矩阵指令还有更具体的要求：某个线程的某个寄存器位置，必须对应指令规定的那个矩阵元素。即使两个布局覆盖了完全相同的矩阵，只要元素分配顺序不同，也可能不能直接用于同一条指令。

### 4.1 检查寄存器片段和半字打包顺序

寄存器片段就是“每个线程持有矩阵中的哪些元素”。Task 20 会逐个核对线程组、warp、lane 和寄存器位置对应的逻辑坐标。

对 RS 的 16 位 A 输入，两个元素按指定的低半字/高半字顺序组成一个 32 位寄存器。本实现的 A 布局槽位按 16 位元素计数，因此一个基本片段的 8 个槽位对应 4 个打包寄存器，而不是 8 个独立的 32 位寄存器。

例如，某个位置要求低半字放元素 x、高半字放元素 y。如果把它们交换，矩阵的元素集合仍然完整，但指令读取的坐标已经不对。Task 20 不会只凭“没有少元素”就接受这种方案。

测试中也专门修改了一个仍满足通用覆盖要求的布局，交换其逻辑坐标位，确认实际指令布局验证会拒绝它。

### 4.2 检查线程组和大 tile 的拼接

当前 MMA 支持单个线程块内的 128、256、512、1024 线程，每个 warp-group 固定由 4 个连续 warp 组成，也就是 128 个线程。只看线程总数相同还不够，组内结构也必须正确。

回到 `128×128×64` 的例子：如果使用 128 线程，就是一个 warp-group。按当前规则，可以选择 `64×128×16` 的基本指令形状，沿 M 重复 2 次、沿 N 重复 1 次、沿 K 重复 4 次。

```text
整个计算块：M=128，N=128，K=64
基本形状：  M=64， N=128，K=16
重复次数：  M=2，  N=1，  K=4
```

因此布局契约记录的是 8 次基本矩阵乘加所需的组织关系。这里说明的是静态指令方案，不表示本阶段已经输出了 8 条 GPU 指令或安排好了异步执行顺序。

多个 warp-group 时，FullRow、FullCol、Square 三种 policy 按固定规则划分 M/N 方向。它们目前是确定性选择策略，不是已经经过性能搜索的最优方案。

## 5. Shared descriptor 必须与真实存储地址一致

Descriptor 可以理解为“交给矩阵指令的寻址说明书”：它告诉指令从哪里开始、按什么间距读取、使用哪种存储组织。

Task 20 不仅检查说明书字段齐全，还根据说明书重建访问地址，逐点比较它与实际 StorageLayout 的地址是否一致，同时检查对齐和范围。

当前覆盖 K/MN 两类 major，以及无 swizzle、32/64/128 字节 swizzle 的规范模板。swizzle 是一种按地址位重新组织存储的方式；本任务验证其寻址正确性，不评价哪一种一定更快。

### 5.1 具体例子：切片变小，父存储的间距却没有变

已有测试从一个 `128×128` 的 bf16 shared buffer 中，取出起点为 `[0,16]`、大小为 `64×32` 的切片，并使用指定的 K-major、32 字节 swizzle 存储布局。

在这个具体布局下，两个 K 方向原子块的起点，相对于共同底层存储分别为：

```text
第一个原子块：4096 字节
第二个原子块：8192 字节
实际间距：   4096 字节
```

如果只看到切片有 64 行，就错误地用 `64 × 16 个 bf16 元素 × 2 字节 = 2048 字节` 推算块间距，会把第二个起点写成 6144，而不是 8192。

Task 20 会拒绝这个错误 descriptor。原因是：切片只改变“使用父存储的哪部分”，不会自动重新紧密排列父 buffer 的数据。

这些数字来自该指定布局的证明测试，不是所有 bf16 矩阵的通用地址公式。相关测试还覆盖了非零起点、swizzle phase 错误、地址越界与对齐不足。

另外，指令“需要更强对齐”不能反过来证明底层内存“已经具备更强对齐”。目标生成候选时必须使用已有的根对齐证据，不能自行提高保证。

## 6. 只在消费位置转换，不随意改掉外部数据的布局

矩阵指令需要特定布局，但一个 Tensor 可能还被其他操作使用。不能因为其中一次使用是 MMA，就把生产者整体改成 MMA 布局。

Task 20 保留了“生产者值”和“当前消费位置”的区别。

例如，外部已经产生 A 和 init，它们各自具有明确布局，但与当前 MMA 所需布局不同：

```text
外部 A：原有布局 ── convert_layout ──→ MMA 的 A 消费布局
外部 init：原有布局 ── convert_layout ──→ MMA 的 init 消费布局
                                           │
                                        SameLayout
                                           │
                                      MMA result 布局
```

这里有两种不同关系：

- 外部生产者到 MMA 消费位置是 `Convertible`：允许在这个使用点插入显式转换。
- init 的消费位置与 result 是 `SameLayout`：作为同一次矩阵指令的累加器输入和输出，采用相同编码。

已有专项测试确认：外部 A/init 的显式编码保持不变，MMA 消费前插入两个转换；再次推断不会继续重复插入。

Shared 端则使用布局绑定与地址证明，不因候选不匹配就偷偷复制一份 shared buffer。多个 MMA 共用同一存储时，也会合并允许的有限候选来源，而不是后遇到的操作覆盖前面的布局决定。

## 7. 方案写入实际 IR，并接受独立复验

推断结果不只存在于编译器的临时表中。成功后，操作上保存：

| 属性                        | 保存的信息                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------- |
| `frisk.execution_threads` | 这次 MMA 的线程数                                                                       |
| `frisk.mma_contract`      | 目标、SS/RS、输入与累加类型、基本形状、线程组划分、重复次数、打包规则及 descriptor 方案 |

Tensor 继续使用通用 Distributed encoding，shared 继续使用 StorageLayout。本阶段没有另外实现一套 `MmaEncodingAttr`、`DotOperandEncodingAttr` Tensor 编码类型，而是用“通用布局 + 操作级指令契约”表达专用要求。

写入结果之后，独立验证器只读取实际 IR 的类型、布局、线程和指令属性，重新证明它们相互一致：

- 不重新生成候选来替换错误结果。
- 不猜测缺失的 contract 或线程属性。
- 不把之前求解得到的合法组合缓存直接当作证明。

测试会删除必要属性，或者把 descriptor、线程组、寄存器片段改成不匹配的值，检查系统是否拒绝。错误打包字段还会在类型化属性的结构检查中被拒绝。

所有物化先发生在临时 IR 中，结构检查和实际布局证明都成功后才更新原程序。失败时原 IR 保持不变；推断结果打印、重新解析、再次推断后保持稳定。

诊断也区分两种情况：“发现违反契约的反例”和“受限于表示或证明预算，暂时无法证明”。后者是 Unknown，不会被当作成功，也不等于断言所有硬件实现都不可能。

### 8.2 相比机械迁移旧规则，改进在哪里

可以重点汇报三个设计特点：

1. 存储布局与寄存器分布分开表达，但通过同一条指令契约联合约束。
2. 候选建议与硬正确性证明分开，不能因为某个布局由目标模型或旧代码生成，就默认它合法。
3. 求解答案写入实际 IR 后还要重新证明，不依赖求解器的内部状态才能解释结果。

例如，legacy 分类测试记录了旧 RS A 的 replication=2，而对应 128 线程的新 canonical A 为 replication=1。旧候选保留作历史行为参照，但不能为保持旧输出一致而绕过新的指令契约。

与 TileLang、Triton 的关系和固定版本证据见长期维护的比较文档。这里强调的是 Frisk 已落地的架构组合，不宣称其他系统没有相关能力，也不把共同遵守硬件规则本身说成独创。

### 8.3 尚未包含的能力

- 目标必须显式为 `sm_90a`；新 MMA 路径不支持缺失 target、仅 `sm_90` 或 SM80。
- 当前是静态二次幂整块，M 为 64 的倍数、K 为 16 的倍数、N 至少为 8；不处理动态形状、尾块或隐式 padding。
- 只支持 f16/bf16 输入、f32 累加；不含 f16 累加、TF32、FP8、整数和稀疏路径。
- 不支持 Tensor B、Local MemRef 寄存器模拟或一般 Product 指令布局。
- 单个布局的逻辑点和硬件点枚举各受 65536 预算限制；这是证明规模限制，不是已经完成的寄存器压力、spill 或 occupancy 分析。
- 没有完整 CostVector 性能求解、GPU 指令 lowering、异步同步流水线、GPU 数值执行或性能 benchmark。
- Reduce 迁移留给 Task 21；旧 Buffer Gemm 的自动 normalization 与旧生产接口退役留给 Task 22。

## 9. 可直接用于口头汇报的总结

> Task 20 完成了矩阵乘法向 Frisk 统一布局推断体系的接入。新增的 MMA 操作显式表达输入矩阵、已有累加值和新结果，支持 SM90a 的 shared/shared 和 register/shared 两种输入组织。编译器不再只分别判断各个布局是否合法，而是联合检查 A、B、累加器和线程组是否属于同一套指令方案，并进一步验证寄存器元素顺序和 shared descriptor 的真实地址。外部数据布局不匹配时，可以只在消费位置插入转换；最终方案写入 IR 后还会独立复验，失败则保持原程序不变。本阶段新增 36 个单元测试，已通过既定回归，为后续 Reduce 迁移和 GPU lowering 提供基础，但尚不包含可执行内核或性能领先结论。
